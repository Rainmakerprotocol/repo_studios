# Function Analysis Companion Report Guide

This guide explains how to interpret the JSON companion analysis produced by
`.repo_studios/scripts/producers/generate_function_analysis.py`. The analysis
consumes the structural inventory generated by
`generate_function_inventory.py` and surfaces duplicate implementation signals
for faster refactoring decisions.

## Artifact Overview

Each analysis run writes two files inside `<target>_index/`:

- `<target>_analysis-YYYY-MM-DD.json`: dated payload with full findings.
- `latest.json`: pointer that mirrors the freshest inventory, paired with the
  analysis output for quick consumption.

```text
<target>/
  <target>_index/
    <target>_index-YYYY-MM-DD.json
    <target>_analysis-YYYY-MM-DD.json
    latest.json
```

## Metadata Fields

| Field | Description |
| ----- | ----------- |
| `schema_version` | Integer for schema evolution tracking. |
| `metadata.analysis_version` | Semantic version of the analysis producer. |
| `metadata.generated_at` | ISO-8601 timestamp (UTC) when the analysis ran. |
| `metadata.source_index_file` | Absolute path to the inventory JSON that was analyzed. |
| `metadata.source_index_hash` | SHA-256 digest of the inventory payload for tamper detection. |
| `summary.duplicate_groups` | Count of duplicate clusters discovered. |
| `summary.total_duplicate_functions` | Total function definitions across all duplicate groups. |
| `summary.total_files_scanned` | Number of Python files present in the inventory. |

## Findings Structure

Each entry in `findings[]` represents a duplicate group surfaced from the
inventory. Core fields include:

- `id`: Stable identifier (`duplicate_function::<slug>`).
- `kind`: Currently always `"duplicate_function"`; reserved for future heuristics.
- `severity`: Defaults to `"medium"`; adjust as new categories emerge.
- `summary`: Human-readable string describing the duplicate counts.
- `details`: Machine-readable context including the canonical `signature`,
  shared `docstring`, and per-instance `line_counts`.
- `metrics.duplicate_count`: Size of the duplicate cluster.
- `action_items[]`: Recommended next steps. Consumers should act on the `targets`
  array formatted as `<relative_path>:<line>` entries.
- `instances[]`: Per-implementation metadata copied from the inventory. Each
  instance contains `path`, `line`, `signature`, `docstring`, and `line_count`.

### Recommended Consumer Workflow

1. Sort or filter `findings[]` using `metrics.duplicate_count` to prioritize
   high-duplication areas.
2. For each `action_items[]` entry, open the listed `targets` in an IDE to
   review implementations side-by-side.
3. Use the shared `signature` and `docstring` from `details` to confirm the
   grouping context before refactoring.
4. Leverage `instances[].line_count` to spot potential refactoring anchors
   (e.g., unusually large or small variants).
5. After remediation, regenerate the inventory and analysis to confirm the
   duplicate group is resolved.

## Failure Modes

The analysis exits non-zero when:

- The specified target lacks an inventory directory or JSON artifact.
- The inventory JSON fails to parse or contains invalid schema data.
- File system or permission errors prevent writing the analysis output.

Consumers can rely on the analysis run to be idempotent and atomic—the script
cleans stale dated outputs, uses temp files during writes, and logs clear
progress metrics (`duplicate_groups`, `duplicates`).

## Integrating With Tooling

- **Automation**: The Make target should invoke the inventory producer first,
  then the analysis producer, leaving the paired artifacts and `latest.json`
  pointer in place.
- **CI Validation**: Validate both artifacts against the JSON schemas under
  `docs/schemas/` and ensure only the freshest dated files remain.
- **IDE Extensions**: Consumers can parse `latest.json` to discover the most
  recent inventory without globbing through dated filenames, then use
  `metadata.source_index_file` inside the analysis for provenance.

## Future Enhancements

- Additional findings (hotspots, anomaly detection) can reuse this structure by
  adding new `kind` values and `details` envelopes.
- Severity levels can be tuned per finding type once additional heuristics land.
- Consider emitting diffs or remediation suggestions once duplicate resolution
  workflows are automated.
